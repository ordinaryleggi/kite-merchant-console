# 04 · 商家服务管理台

PRD 1.0 · 2026-10-18 · 运行基础设施 · 第一批或第二批  
状态：设计提案，未实现/未付款/未提交。先读[总体接入设计](../总体接入设计.md)与[接口事件约定](../接口与事件约定.md)。

## 1. 用户与真实场景

**用户：**同时经营多个 x402 服务、需要管理部署和价格的开发者与小团队。

**第一次使用：**开发者已有三项服务，需要把其中一项改价、部署新版本并暂停错误端点；管理台展示实际生效配置和真实试单，不让坏示例继续留给买方。

**问题：**清单、环境变量、部署版本和运行状态分散；价格已改但目录示例没改、服务挂了仍显示可用、密钥误入清单等问题难以管理。

**Kite 接入价值：**经营自有 Kite 服务的控制台。复用官方目录、manifest 与既有网关，不再建一个“官方目录替代品”，也不假定能修改 Kite 内部管理系统。

## 2. MVP 范围

**P0，首版必须完成：**

- 导入自有服务与仓库，维护 manifest 和部署配置；按官方闭合 schema 校验。
- 报价、网络、资产和 endpoint 示例分别版本化，发布前执行预检和获批试单。
- 首版只接一个部署后端；应用显示 desired/applied 两种配置，不把“生成配置”写成“已上线”。
- 服务健康、付费路径、交付失败和价格变更记录；可暂停自有端点或回滚版本。

**P1，有真实反馈后再做：**

- 接入对账工具查看细分异常，支持第二部署后端。
- 生成服务目录提交材料；官方收录状态由真实 PR/目录结果确认。

**首版排除：**不运营新钱包、不建立平行官方目录、不一开始兼容所有云、不自动替维护者提交外部 PR。

## 3. 完整用户流程

1. 维护者证明对服务/部署的控制权，导入当前版本。
2. 编辑清单与报价，校验字段并生成差异。
3. 预检 402、网络和付费示例，人工批准必要的试单预算。
4. 通过受限部署凭证发布，回读端点确认生效。
5. 生成 service.yaml 和真实示例材料供提交。
6. 发现交付失败时先暂停受影响版本；回滚与重新开放都记录真实检查结果。

## 4. Kite 能力接入

| 官方能力 | 接入方式 | 保存与验证 |
|---|---|---|
| 服务定义 | service.schema.json 与 service.yaml | network/pay_to/endpoints/source/status；不添加自创字段到闭合清单 |
| 试单 | Passport 已批准会话与 execute | 真实付款、业务产物、网络/资产，不以 mock 提升状态 |
| 发布资料 | 官方服务 PR/目录流程 | 管理台仅生成材料；目录收录需外部确认 |

**接入前置：**所有涉及真实付款的路径先完成 G0，固定 network/asset/facilitator/CLI/账户环境；见总体接入设计。真实身份或 Runtime 不可得时明确 blocked，不能用 mock 替代。

**授权边界：**应用与业务权限自己验证；Passport 的 passkey 批准保留给真实用户；本轮 PRD 编制不发起任何授权或支付。协议实例、金额、会话和示例均以现场预检与实际输出为准。

## 5. 接口与数据

**拟提供接口：**GET/POST /services、POST /services/{id}/releases、POST /releases/{id}/preflight、POST /releases/{id}/apply、POST /releases/{id}/rollback。内部服务配置可包含扩展字段，导出 manifest 只保留官方允许字段。

**核心对象：**Service、EndpointVersion、PriceVersion、ManifestVersion、DeploymentTarget、Release、ProbeRun、CatalogSubmission。status=draft/testnet/live 依据真实证据转换，不由按钮直接改成已验证。

operation_id、付款证据、业务版本及产物按公共事件契约关联。接口/包名属于本项目设计，不代表官方已经发布同名能力。

## 6. 状态与恢复

DRAFT → VALIDATED → PREFLIGHTED → DEPLOYING → APPLIED → VERIFIED；另有 DRIFTED、PAUSED、ROLLBACK_PENDING、FAILED。内部发布状态与官方 manifest 生命周期分开。

- 端点运行配置与清单不一致时标 drift；网络测试受阻就不发布为已互通。
- 密钥存储用受控 secret 引用，不导出到 manifest、README 或日志。
- 回滚失败不能显示已回滚；暂停只影响自己控制的服务，不能假称全局目录已下架。

任何付款未知均不能通过换 key 自动重买；任何产物恢复都需要原权限。测试桩中的假付款不产生真实交付承诺。

## 7. 开发任务拆分

- 04-T01：导入模型、schema 校验与版本差异。
- 04-T02：接一个实际部署后端，实现 desired/applied 回读。
- 04-T03：实现预检和手动批准试单流程。
- 04-T04：实现暂停、回滚与漂移检测。
- 04-T05：运营两个自有服务，导出可审阅提交材料。

**投入粗估：**5–7 人周。先做 M0 兼容与样本验证，再做独立核心、真实互通及发布；外部批准、环境开通和审核不计入可承诺工期。

## 8. 界面与使用体验

服务列表、发布差异、实际状态和故障入口四页；按“可执行的运维动作”设计，不堆泛指标。

在需要用户决定时展示价格、范围、权限和失败状态；普通产品页面不堆协议实现细节，技术证据留在诊断/报告页。

## 9. 验收与演示

下面是目标，尚未运行或达成。

- M01：未知 manifest 字段、错误网络和无效示例在发布前被挡住。
- M02：一次真实部署、价格回读、版本回滚和配置漂移都可演示。
- M03：只有真实试单和可访问产物支持已验证状态，凭证注明环境。
- M04：操作者权限、部署凭证隔离及修改审计经过检查。

**完整演示：**修改一项服务价格，预检发现示例错误，修复后部署试单；再演示回滚与清单/运行漂移。

**试用观察：**一次安全发布用时、配置漂移数量、失效示例被发现的时间和重复运维步骤。

## 10. 提交与独立性

商家工具；不自动等于一个已开放的 Bounty 赛道。官方 tooling 贡献或独立生态仓的登记范围需确认。

项目核心包括本 PRD 定义的模型、业务引擎/状态/断言与样本；支付和基础依赖可正常共享，不复制其他参赛实现换名。EC 映射、活动审核与真实贡献是否被统计分别跟踪，不用本 PRD 保证收录。
